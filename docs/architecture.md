# Архітектура модуля

## Схема

```text
Адміністратор одержувача
        │
        ▼
Admin UI ──► локальний REST ──► Analyzer / Jobs / Product Sync
                                      │              │
                                      │              ├─► WooCommerce товари
                                      │              └─► журнал задач
                                      ▼
                              HTTPS REST client
                                      │
                                      ▼
                     WooCommerce REST сайту-донора
                              │               │
                              ├─ products     └─ variations
                              ▼
                         WooCommerce каталог
```

Основний сценарій потребує плагін лише на одержувачі та використовує стандартні read-only маршрути `wc/v3`. Якщо плагін також встановлено на донорі, клієнт автоматично може використати компактні маршрути `lwps/v1` як розширений протокол.

## Ідентифікація

У meta `_lwps_uid` зберігається окремий UUID для кожного `product` і `product_variation`. У read-only режимі це детермінований UUID v5 від канонічного URL донора, типу об'єкта та віддаленого REST ID. Він не дорівнює локальному WordPress ID, стабільно повторюється при кожному аналізі й не потребує запису на донорі.

Ідентифікація:

1. Одержувач обчислює стабільні source UUID без зміни донора.
2. Після імпорту UUID записується в meta локального батьківського товару.
3. Для кожної варіації створюється окремий source UUID і записується в meta варіації.
4. SKU не запитується, не порівнюється, не синхронізується та не використовується для зв'язування.

## Дані донора

У стандартному режимі `GET /wp-json/wc/v3/products` повертає посторінковий каталог, а `GET /wp-json/wc/v3/products/{id}/variations` — варіації. Адаптер нормалізує ці відповіді у внутрішній snapshot, додає source UUID та обчислює канонічні хеші. Обробляється по 20 товарів за крок.

Під час виконання задачі повний товар повторно читається за REST ID, збереженим у самій позиції журналу. Тому retry не залежить від поточної таблиці змін.

У розширеному режимі сумісними залишаються `GET /wp-json/lwps/v1/manifest`, `GET /wp-json/lwps/v1/product/{uuid}` та необов'язковий `POST /wp-json/lwps/v1/bootstrap`. Останній потребує write-доступу й не показується для read-only підключення.

## Аналіз

Одержувач порівнює хеші основних даних та кожної варіації. Визначаються:

| Статус | Умова |
|---|---|
| `new` | UUID донора відсутній локально |
| `update` | основні дані або варіації відрізняються |
| `missing_variations` | на донорі є варіації, яких немає локально |
| `local_changes` | локальний хеш змінився після останньої контрольної точки |
| `locked` | товар заблокований і має відмінності |

Незмінені товари не записуються до таблиці `wp_lwps_changes` і не відображаються в інтерфейсі.

Admin UI відкриває етапи послідовно: **Підключення → Аналіз → Зміни й дія → Журнал**. Збереження і перевірка REST-доступу є однією дією. Під час пакетного аналізу інтерфейс показує живий прогрес, кількість опрацьованих товарів і час виконання; до списку змін можна перейти лише після успішного завершення.

## Операції

| Режим | Основні дані | Існуючі варіації | Нові варіації | Видалення відсутніх |
|---|---:|---:|---:|---:|
| Імпорт | так | — | усі | ні |
| Основні дані | так | ні | ні | ні |
| Варіації | лише атрибути варіативності | так | так | ні |
| Відсутні варіації | лише атрибути варіативності | ні | так | ні |
| Повний перезапис | так | так | так | опційно |

Перед створенням задачі `preview` рахує очікувані створення, оновлення, видалення та пропуски. Адміністратор може перевірити вибрані галочками товари або явно запустити всі товари, придатні для вибраного режиму. Порожній список UUID не трактується як масова команда без явного `scope=all`. Заблоковані товари пропускаються, доки адміністратор явно не ввімкне примусову операцію.

## Черга і журнал

`wp_lwps_jobs` зберігає загальний стан задачі, а `wp_lwps_job_items` — кожний товар окремо. Пакет обробляє до п'яти товарів за крок. Для фонового продовження використовується WooCommerce Action Scheduler, із fallback на WP-Cron. В інтерфейсі це один повноширинний екран: операція вибирається зі списку, а її прогрес і журнал відображаються разом.

Стани елемента: `pending → running → success|failed`. Atomic claim не дозволяє двом воркерам одночасно обробити одну позицію. Невдалі елементи переводяться назад у `pending` окремою командою повтору.

## Межі автоматичного перенесення

Стандартні поля WooCommerce, категорії, теги, атрибути, зображення та проєктні scalar meta переносяться автоматично. Довільні meta-поля додаються через `lwps_synced_meta_keys`.

Поля, які містять локальні attachment ID, post ID або складні зв'язки, потребують окремого адаптера, щоб замінити донорські ID на локальні. Видалення батьківських товарів автоматично не виконується; видалення варіацій є опційним і переміщує їх у кошик.
